# 怎么验证我们说的是真的

这份文件写给要评估这套系统的人。它不给参数、不给阈值，只给**判断方法**——你应该拿什么标准
去检验，以及我们能提供什么证据。

## 一、公开层面能自己核对的

1. **样本报告内部一致性**：任取三条结论，看每条是否都能跳回具体帧。跳不回去的，就是装饰。
2. **标注纪律**：找报告里带百分号或"概率"字样的值。实测值和模型推算值，是否被清楚区分？
   如果所有数字长得都一样，说明这套系统在混着讲。
3. **同一个数字在多个视图里是否自洽**：比如控球比例、传球次数，在不同视图里出现时应一致。
4. **口径说明**：报告是否写清每项指标的统计口径。写不清口径的指标，无法证伪。

## 二、POC 层面能验的（一场比赛，48 小时）

给一场比赛，我们回一整套产出。你验这几件事：

| 验什么 | 怎么验 |
|---|---|
| 人是不是对的 | 挑 10 个你认识的球员，看报告中的身份归属是否正确 |
| 位置是不是对的 | 挑 3 个明显场景（一次越位、一次角球、一次反击），看沙盘里的站位与真实画面是否对得上 |
| 结论有没有依据 | 任取一条战术结论，点回原始帧，判断"这条结论配不配得上这一帧" |
| 交付是否可核对 | 报告是否给出统计口径、是否区分实测与推算 |
| 不理想的部分是否被承认 | 我们是否主动标注了低置信片段，而不是把不确定的部分藏起来 |

**我们想要的反馈是"哪一条不对"**，而不是"好不好用"。前者能让我们改进，后者没法验证。

## 三、NDA 层面能看的

签署 NDA 后开放私有仓库，授予具名个人的限时只读权限。在那次会话里，我们会：

- 走一遍完整流水线，讲清每个阶段的输入输出与失败处理；
- 现场跑一场你指定的比赛，而不是只演示准备好的样例；
- 说明精度是怎么测的、测在哪批数据上、失败案例长什么样；
- 回答"这个方法在我们的场景下会不会失效"这类问题。

**不给的东西也说清楚**：训练数据的来源明细、第三方模型的具体标识、我们能给出的性能上限承诺。
前两项涉及他人权利，第三项在没有你的真实素材前给不了。

## 四、三条我们不会做的事

1. **不会承诺胜率。** 这套系统提供的是客观、可回看的战术资产，不承诺比赛结果。
2. **不会用模拟值冒充实测值。** 凡是推算，报告内标注。
3. **不会把低置信片段藏起来。** 数据不足的部分，标注比修饰更有价值。

## 五、给你的判断标准

如果你只记一句话：**看这套系统在"它不知道"的时候怎么表现。**
一套可靠的分析系统，在证据不足时会沉默或标注；一套不可靠的，会给你一个漂亮的数字。
这是我们最希望被检验的地方。
